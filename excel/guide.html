The workbook is generated, not maintained. Every run rebuilds it from the database as it stands, so nothing in it should be edited by hand — the next run will not keep the change. Anything that should be different belongs in the script.

What is in it

SheetWhat it is for

One table, not a sheet per day

Only the hidden sheet holds values. Daily reads it by formula, so changing the date in the dropdown recalculates the same table in place — one set of formatting, one print layout, however many days accumulate.

Rows are ordered by absolute variance descending, so whatever needs attention is at the top rather than wherever the alphabet put it. Variance is grey at zero and red from one pack, getting heavier at five and again at ten. Ctrl+P prints the day on screen on a single page, with the header row repeated.

branch_id and pos_description are gone. So is Added: add_in is always zero because the count screen no longer collects deliveries, and a column of zeros would only imply something had been checked. It is still on the hidden sheet.

Zero and unknown are not the same thing

This is the thing to understand about every figure in here. Variance comes from the view, which means it is blank whenever the view cannot work it out — and that happens for two quite different reasons:

ReasonWhat to do
No POS sales loaded for that dayImport that day’s sales report
No opening figure — the first count of a productNothing. It fills in from the next consecutive count
Which is why it shows an em dash, not a zero

A blank cell in a spreadsheet reads as “nothing wrong”. These days are “not checked”, which is a different thing and the one worth knowing about. The summary line says in plain English which of the two applies, and the totals skip those rows rather than counting them as agreement.

Trends

Variance by product across every counted day, sorted by how many days each product was off before how large the gap was.

A leak outranks an event

Five nights off by one pack is a leak worth chasing. One night off by five is an event. The leak sorts above the event, which is the whole reason this sheet is not just Daily with more columns.

Days off counts only days that could actually be checked, so a product that has never had a POS figure reads as a dash rather than as a confident nil.

There is a test too — python3 verify_workbook.py. It matters because the live database has no variance in it yet, so the ranking, the totals and the colouring would otherwise ship having never run. It feeds the builder a day set shaped to exercise them and checks the answers.

Variance in ringgit

Needs a price per pack, which means running 10_prices_and_opening_date.sql. Until then the RM column and Opening from read as unavailable and everything else works.

Where the price livesWhy there
pos_sales_daily.unit_priceWhat the pack sold for on that day. Filled automatically from the next sales report imported — the importer already reads the price to prove the quantity, so it costs nothing to keep
product.unit_priceThe current list price, and yours to set. The fallback, and the only answer for a product that had variance but sold nothing that day — which is exactly the shrinkage case worth pricing
Why not just one price column

Cigarette prices move, and a duty change revalues the whole gondola overnight. Valuing August’s variance at today’s price would quietly restate history every time someone updated a price. So the price is recorded where it is observed, and the workbook can show which one it used.

Reading the variance

0
Agreed. The shelf and the POS tell the same story.
+12
More left the shelf than was sold. Shrinkage, a miscount, or stock that went out without being recorded.
−40
The POS sold more than the shelf lost. Nearly always a delivery that was not recorded as add_in.
—
Not known, and not zero. Either no POS sales were loaded for that day, or it is the product’s first count and there is no opening to sell down from.

Two things that will skew it

Deliveries are not recorded. The count screen collects one number per product and no longer captures stock added during the day, so add_in is always zero. On any day stock went onto the shelf, Sold (counted) understates what was sold and the day reads as negative variance.

Counts must be consecutive. Opening is the previous submitted count’s closing, whatever date that was — skip a day and two days of sales fold into one, which reads as a large variance the day after the gap. That is what Opening from in the summary is for: if it is not the day before, treat the figures with suspicion.

If something looks wrong

Everything reads as a dash
No POS sales are loaded for that day, or it is the first count. The summary line above the table says which.
Variance RM is blank everywhere
Migration 10 has not been run, or product.unit_price has not been set.
The dropdown is missing recent days
The workbook is a snapshot. Re-run build_workbook.py.
A large variance out of nowhere
Check Opening from in the summary. A skipped day folds two days of sales into one figure.
My edits disappeared
Expected — the file is regenerated. Put the change in build_workbook.py so it survives.
